## 1. 判定語彙

- **範囲履歴あり**: 過去会話・作業記録でID範囲の成立/追加/維持指示が確認されている。
- **個別本文未回収**: そのIDに対応する要求・試験名・前提・期待結果を会話記録等からも回収できていない。
- **会話記録から再回収**: 過去会話の記録に個別定義が残っている状態。原本文書・当時の正式承認までは未検証。
- **正式性未確定**: 範囲履歴だけでは、個別行の最終承認・廃止・置換を判断できない。
- **実装対応未確認**: 現行テストコードとの一対一対応を示す根拠がない。
- **V082未対応付け**: V082-001〜050との重複・包含・未カバー関係がまだ確定していない。
- **参照専用・実行不可**: 来歴は残すが、個別本文・承認・テスト実物を確認できないため現行受入のPASS/FAIL対象にしない凍結状態。未作成・不存在を意味しない。

### 10.1 判定語彙

「番号の範囲が会話に登場した」ことと、「各番号の要件本文・テスト・正式資料が実際に作成された」ことを区別する。未発見を自動的に「存在したが紛失」と扱わず、未作成の可能性も残す。

| EXISTS_CONFIRMED | 対象の原文・ファイル・Issue/PR記録・実装テスト等の実物を確認 | 対象そのものの内容と出所を取得できる |

### 12.2 不足証拠の処理決定

DB-001〜124は、全IDをEvidence Ledgerに残す。ただし、原文を回収できないIDを推測で再構成したり、受入試験として実行可能な状態に見せたりしない。

個々のIDには、以下の独立した属性を付けて管理する。

1. Provenance Status: 来歴確認済み / 来歴の参照記録のみ / 来歴未確認 / 正式番号対象外。
2. Content Status: 原文回収済み / 会話由来短縮定義のみ / 未回収 / 未作成を直接確認。
3. Approval Status: 正式承認確認済み / 承認記録未回収 / 未承認 / 対象外。
4. Test Artifact Status: テスト実物確認済み / テスト記録のみ / 実物未回収 / 未作成を直接確認。
5. Operational Disposition: 現行受入基準 / 参照専用・実行不可 / 新規根拠待ち / 正式体系対象外。

この分離により「番号の来歴は確認できるが、本文は未回収」「維持指示はあるが、試験実物は未確認」のような状態を正しく表現する。

### 12.3 原文・根拠が回収できないIDの扱い

**決定方針: 未回収の旧IDは削除せず、参照専用の未検証レガシー項目として凍結する。**

- Content Status = NOT_RECOVERED
- Approval Status = NOT_VERIFIED（承認記録が回収できない場合）
- Test Artifact Status = NOT_VERIFIED（試験実物が回収できない場合）
- Operational Disposition = REFERENCE_ONLY_NOT_EXECUTABLE

上記は個別本文・承認・テスト実物を回収できない場合の運用ラベルであり、「未作成」「不存在」「不合格」を意味しない。
- 当該IDを現行受入試験のPASS / FAIL判定対象にしない。
- 内容を推測して穴埋めしない。
- 近似する現行要件へ黙って統合・置換しない。
- 旧IDを再利用・再採番しない。
- 後から一次資料が見つかった場合は原文・出所・版・日付を記録し、再審査して状態を更新する。
- 「未作成」を直接示す証拠が見つかった場合は NOT_CREATED_CONFIRMED とし、旧IDは履歴台帳に残したまま RETIRED_NOT_CREATED とする。検索0件だけでこの状態にしない。

### 12.4 新しい受入試験での不足カバー

旧IDの内容が不明なまま、旧IDを再現する試験を作ってはならない。現行システムに必要な試験カバーが別途必要と判断された場合は、次の順序で扱う。

1. 現行の承認済み仕様または統括決定から試験目的・期待結果を特定する。
2. 既存旧IDとの対応が証拠で確認できる場合のみTraceabilityを記録する。
3. 対応が確認できない場合は、旧IDの代替を称さず、新しい独立Test IDとして提案する。
4. Test IDの採番・受入基準化は統括の承認後に行う。
5. 旧IDは履歴上残し、新Test IDへ番号や本文を転用しない。
